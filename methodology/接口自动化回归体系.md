# 接口自动化回归体系

> 定位：接口变更后自动验证功能正确性，融入 CI/CD，测试不通过阻断发布。
> 本文只保留通用方法，不含具体业务与组织信息。

## 一、核心价值

手工回归与自动化回归的对比（数字为量级参考）：

| 维度 | 手工回归 | 自动化回归 |
|------|---------|-----------|
| 执行时间 | 小时级 | 分钟级 |
| 覆盖率 | 抽样式覆盖 | 可做到全接口 |
| 执行频率 | 周 | 日 / 每次部署 |
| 人力 | 持续占用 | 一次建设，趋近于零 |

## 二、分层架构

```text
触发层    代码提交(Webhook) / 定时(Cron) / 手动
              │
执行层    主入口 run_tests.py
              ├── L1 冒烟测试（核心接口 × 关键上下文，分钟级，要求 100% 通过）
              ├── L2 回归测试（全接口 × 全上下文抽样，十余分钟级，通过率 ≥ 阈值）
              └── 报告生成
              │
引擎层    请求构建 Builder / 响应验证 Validator / 报告生成 Reporter
              │
被测层    测试环境 / 生产环境（生产只跑只读接口）
              │
输出层    HTML 报告 / JUnit XML / JSON 数据 / 日志
```

要点：

- **冒烟不过就终止**：L1 失败直接阻断并告警，不浪费 L2 的执行时间。
- **引擎与用例分离**：请求构建、验证、报告是通用引擎；用例只是配置和数据。
- **多格式输出**：HTML 给人看，JUnit XML 给 Jenkins 消费，JSON 给后续分析。

## 三、测试矩阵

```text
测试组合 = 接口 × 环境 × 上下文维度（地区 / 应用版本 / 租户等）
```

- 参数化自动展开，避免手写穷举。
- 冒烟取矩阵的代表性子集，回归取全量或分层抽样。
- 上下文维度按业务影响面选取，不是越多越好——每加一个维度，组合数翻倍。

## 四、推荐目录结构

```text
regression-test/
├── config/          # 环境变量、全局配置、测试数据
├── core/            # 请求构建 / 响应验证 / 执行器（引擎层）
├── tests/           # 用例（冒烟 / 回归）
├── reports/         # 报告产物（自动生成，不入库）
├── run_tests.py     # 主入口
├── requirements.txt
└── Jenkinsfile      # Pipeline 代码化
```

本仓库的 [code/api-testing](../code/api-testing/) 即 `core` + `tests` 的最小可用实现。

## 五、落地顺序建议

1. 先跑通一个接口的端到端流程（请求 → 断言 → 报告）。
2. 再扩展用例覆盖面，先核心接口后全量。
3. 最后接 CI 与门禁（见 [[CI集成与质量门禁]]）。

> 教训：不要一开始就追求平台和页面，脚本稳定运行产生价值后，再考虑平台化。
