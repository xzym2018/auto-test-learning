# 接口契约回归与兼容性测试

> 定位：验证「App/调用方依赖的接口是否保持契约兼容」，不替代业务功能正确性验证。

## 一、回答什么问题

发版或部署之后：

- 接口是否仍可用；
- 响应结构是否仍兼容老版本调用方；
- 关键字段是否缺失、字段类型是否变化；
- 变更是否需要阻断发布。

## 二、契约断言的五个层次

| 层次 | 内容 | 示例 |
|------|------|------|
| 1. 状态码 | HTTP 状态符合预期 | 200 / 400 / 401 / 404 |
| 2. 必填字段 | 契约字段必须存在 | `id`、`name` 不缺失 |
| 3. 字段类型 | 类型不得漂移 | string 不能变 number |
| 4. 结构基线 | 与已确认基线 Diff | 新增/删除/改名字段 |
| 5. 业务断言 | 少量核心规则 | 版本门槛、枚举合法值 |

前四层是机械校验，可全自动；第五层需要业务知识，只对核心接口补充。

## 三、基线机制（核心）

```text
真实响应 → 提取标准化 Schema → 与已确认基线 Diff → 输出差异
```

基线生命周期：**草稿 → 人工确认 → 启用 → （可回滚 / 废弃）**。

关键规则：

- **基线变更必须人工确认**：Diff 只负责发现差异，对错由人判断；确认后更新基线，形成闭环。
- **Schema 提取的坑**：`null`、空数组、动态 Map 会造成误判（本次采样没有不代表字段不存在）。
- **样本充分性**：单次响应可能遗漏 optional 字段；未充分采样前，Diff 结果只告警不阻断。
- **无基线状态**：首次运行的接口没有基线，结果记为独立状态，聚合时按 WARNING 处理，不能直接判失败。

## 四、风险分级与处置

| 级别 | 含义 | 处置 |
|------|------|------|
| Blocking | 字段缺失/类型变化等破坏性变更 | 阻断发布，必须处理 |
| Warning | 新增字段、无基线等需关注项 | 告警，人工确认 |
| Info | 正常或提示性信息 | 记录留档 |

每条差异要有终态：**确认变更 / 缺陷 / 误报 / 基线更新 / 忽略**，否则告警无法闭环。

## 五、能力边界（避免过度承诺）

一期只做、且应该明确声明只做：

- 固定请求模板 + 响应契约校验；
- 只读接口先行，生产环境不跑有副作用（写/删/推送/扣费）的接口。

不承诺：

- 没有 OpenAPI/人工 Schema 时自动发现完整请求契约；
- 证明所有业务分支与 optional 字段全覆盖；
- 未经过观察期就直接用于正式发布阻断（先非阻断运行，治理误报后再开阻断）。

## 六、通用化模型

对接 CI 或平台时，输入输出保持稳定：

```text
输入: appId / appVersion / envId / regionCode / suiteId / triggerSource / buildNo / operator
输出: runId / status / result / failureLevel / summary / diffReport
```

调用方上下文（哪个 App 包）只作为测试集筛选条件，不作为系统主轴——否则平台会被单一业务绑死。
