# CI 集成与质量门禁

> 定位：让自动化回归在流水线中自动触发，结果能阻断发布，且告警到达人。

## 一、Pipeline 阶段

```text
Checkout(拉代码) → Setup(装依赖) → Smoke(冒烟) → Regression(回归) → Report(报告) → Notify(通知)
```

- **Smoke 失败即终止**：不再执行回归，直接告警。快速失败，节省资源。
- **报告双格式**：HTML（HTML Publisher 插件给人看）+ JUnit XML（Jenkins 原生展示趋势）。
- **Pipeline 代码化**：Jenkinsfile 入库，配置随代码版本管理，不靠页面手点。

## 二、触发方式

| 方式 | 适用场景 |
|------|---------|
| Webhook（代码提交） | 主干变更后自动回归 |
| Cron（定时） | 每日全量回归，兜住非代码变更（配置/数据漂移） |
| 手动（页面/API） | 开发自测、接口改造验证 |

## 三、质量门禁

```text
Gate 1 冒烟: 通过率 100%，失败 → 阻断构建 + 告警
Gate 2 回归: 通过率 ≥ 阈值(如98%)，失败 → 记录 + 告警 + 阻断发布
全部通过 → 发布就绪
```

门禁设计要点：

- **阈值要分级**：冒烟是「系统能不能测」，必须 100%；回归允许少量波动（依赖环境稳定性），但要有底线。
- **阻断要有观察期**：新接入的测试集先非阻断运行一段时间，误报治理干净后再开阻断，否则一次误报就会让团队失去信任。

## 四、结果与退出码的映射（易踩坑）

Jenkins 默认把脚本非零退出码判为构建失败。如果测试脚本用退出码表达「有失败用例」，会导致 Warning 级别结果也被判失败。

正确做法：

- 脚本输出**结构化结果文件**（JSON/JUnit XML）；
- Jenkins 读取结构化结果，显式映射为 `Success / Unstable / Failed`：
  - 有 Blocking 失败 → Failed
  - 只有 Warning → Unstable
  - 全部通过 → Success

脚本侧约定：执行异常（环境挂了）退出码非零；用例失败写入结果文件，退出码可保持零，交由结果文件判定。

## 五、凭据与通知

- **凭据管理**：账号、密钥存 Jenkins Credentials，Pipeline 中引用 ID，绝不写进 Jenkinsfile 或代码库。本地调试用 `.env`（已 gitignore），参考 [code/api-testing/.env.example](../code/api-testing/.env.example)。
- **通知到达人**：邮件 / 钉钉 / 企业微信 / 飞书，失败通知必须包含：失败用例、环境、构建号、报告链接，让人一眼能定位。
- **报告归档**：每次构建的报告归档保存，支持历史趋势对比。
